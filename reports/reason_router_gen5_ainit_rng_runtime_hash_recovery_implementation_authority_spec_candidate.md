## Triggering defect

The first authorized CUDA preflight for:

`A6201-R6202`

failed before model forward, backward, optimizer construction, training, or task
evaluation completed.

The parent checkpoint provision/authentication succeeded exactly.

The failure was:

`A_INIT_FROZEN_HASH:6201:70799bcff0e7589fd8863cd767138da7a86e83afadb489c45714c78283c4de14`

The frozen implementation had two A-init authentication layers:

1. reconstruct expected `A_theta.weight` from the requested A-init seed in the
   live process and compare the live wrapper tensor against that reconstruction;
2. additionally compare the live raw tensor-byte SHA256 against a precomputed
   `A_INIT_SHA256` constant generated on a different PyTorch environment.

Layer 1 is the scientifically relevant exact same-runtime identity check.

Layer 2 is not portable across PyTorch environments because raw floating-point
initialization bytes from the same deterministic initialization specification
are implementation/runtime dependent.

The failed preflight therefore exposed a provenance implementation defect, not
evidence that A-init seed separation failed.

## Corrected A-init authentication contract

For every runtime cell:

1. reconstruct the expected A-init tensor in the same live process using the
   exact frozen initialization rule and requested `A_INIT_SEED`;
2. compare the installed live `A_theta.weight`, after the existing frozen
   device/dtype movement semantics, against the same-process expected tensor;
3. require exact elementwise/byte-equivalent identity after normalizing both
   tensors to CPU contiguous representation at the live tensor dtype;
4. record the observed runtime `A_init_sha256`;
5. record the PyTorch runtime version;
6. require B exact-zero initialization;
7. do not compare runtime A bytes against a cross-version precomputed hash.

The three observed PyTorch-2.10 hashes above are diagnostic/provenance evidence,
not universal initialization identities.
